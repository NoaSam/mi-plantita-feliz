## Resumen

La implementación es sólida en su conjunto. El arco completo (hook de datos → BottomTabBar condicional → MapPage → FitBoundsOnMount → PlantMapSheet) está bien ensamblado, sin vulnerabilidades de seguridad detectadas, sin inyección HTML de datos de usuario, y con la separación de eventos correcta entre el canal `mp:pending-classification-resolved` (solo lo consume App.tsx para navegar) y `mp:plant-context-updated` (lo consumen History y useContextCounts para refetch). ## Warnings

### WR-01: `useWildPlantsWithCoords` no escucha eventos de clasificacion — los pins del mapa no se actualizan en vivo

**Archivo:** `src/hooks/use-wild-plants-with-coords.ts` (todo el archivo) + `src/pages/MapPage.tsx`

**Problema:** `useContextCounts` suscribe a `mp:plant-context-updated` y a `mp:pending-classification-resolved` para refetch reactivo, lo que hace que la tab "Mapa" aparezca sin reload (SPEC-AC2 cumplido para el BottomTabBar). Sin embargo, `useWildPlantsWithCoords` no tiene ese listener, y `MapPage` tampoco lo añade. Si el usuario clasifica una planta como _wild_ desde otra pantalla y luego navega a `/mapa` en la misma sesión, los pins del mapa solo se actualizan si el componente se remonta (nueva navegación), no de forma reactiva en una instancia ya montada.

En la práctica el escenario es poco probable porque el flujo normal (clasificar en `/` → tab Mapa aparece → tap en tab → MapPage se monta fresco) ya re-ejecuta el hook al montarse. Pero si el usuario tiene `/mapa` abierto en background y clasifica en otra tab (mobile multi-tab), los pins quedan stale hasta reload.

**Fix:** Añadir el mismo listener de eventos en `useWildPlantsWithCoords` que ya existe en `useContextCounts`:

```ts
// En useWildPlantsWithCoords, después del useEffect([load]):
useEffect(() => {
  const handler = () => load();
  window.addEventListener("mp:pending-classification-resolved", handler);
  window.addEventListener("mp:plant-context-updated", handler);
  return () => {
    window.removeEventListener("mp:pending-classification-resolved", handler);
    window.removeEventListener("mp:plant-context-updated", handler);
  };
}, [load]);
```

### WR-02: `useContextCounts.load()` no llama `setIsLoading(true)` al inicio del bloque user-present

**Archivo:** `src/hooks/use-context-counts.ts:54-106`

**Problema:** El hook inicializa `isLoading` en `true` y lo resetea a `false` al terminar, pero la función `load()` no vuelve a poner `isLoading` en `true` antes de las 4 queries paralelas. En el primer render todo va bien (estado inicial = `true`). Pero al llamar `refetch()` manualmente o via evento, el hook ejecuta `load()` sin señalizar la carga. Los consumidores (BottomTabBar) ven `isLoading=false` durante el refetch, lo que puede causar un flicker: la tab Mapa desaparece momentáneamente si `wild_with_coords` baja a 0 durante el fetch (ej. revert de clasificación) y luego reaparece. Contrástese con `useWildPlantsWithCoords.ts:71` que sí tiene `setIsLoading(true)` sincrónico antes del await.

**Fix:**

```ts
const load = useCallback(async () => {
  if (!user) {
    if (!mountedRef.current) return;
    setCounts(ZERO);
    setIsLoading(false);
    return;
  }
  // Añadir esta línea:
  setIsLoading(true);  // señaliza carga antes del Promise.all
  const [home, wildWith, wildWithout, unclassified] = await Promise.all([
    // ... queries sin cambio
  ]);
  // ... resto sin cambio
}, [user]);
```

### WR-03: `buildPlantPinIcon()` se llama en cada render de cada `<Marker>` — crea una instancia nueva de `L.DivIcon` por pin por render

**Archivo:** `src/pages/MapPage.tsx:100`

**Problema:** El icono se construye dentro del `.map()` sin memoización:

```tsx
icon={buildPlantPinIcon()}
```

Cada re-render de `MapPage` (ej. al abrir/cerrar el sheet cambia `selectedPin`, lo que re-renderiza el componente) crea `N` nuevas instancias de `L.DivIcon` y las pasa a cada `<Marker>`. react-leaflet compara la prop `icon` por referencia; al cambiar, destruye y re-renderiza los DOM del pin. Con 200 pins esto produce 200 unmount/mount de marcadores en cada interacción con el sheet.

No es un bug de correctitud pero sí puede causar parpadeos visuales observables en usuarios heavy (>20 pins) al abrir el sheet.

**Fix:** Memoizar el icono fuera del componente o con `useMemo`:

```ts
// Fuera del componente, a nivel de módulo (el icono es estático, no depende de props):
const PLANT_PIN_ICON = buildPlantPinIcon();

export default function MapPage() {
  // ...
  // En el Marker:
  icon={PLANT_PIN_ICON}
}
```

O si se prefiere lazily:

```tsx
const plantPinIcon = useMemo(() => buildPlantPinIcon(), []);
// ...
icon={plantPinIcon}
```

### WR-04: `iconAnchor` en `buildPlantPinIcon` diverge del PATTERNS.md de referencia — el pin apunta al centro, no al pie

**Archivo:** `src/lib/build-plant-pin-icon.ts:47`

**Problema:** El comentario en el código dice "bottom-center" y el valor implementado es `iconAnchor: [18, 36]` (centro horizontal, pie del sticker). PATTERNS.md línea 327 especifica `iconAnchor: [18, 18]` (centro-centro). Ambas opciones son válidas por diseño, pero hay una inconsistencia entre la documentación de referencia y el código: el docstring del archivo es incorrecto si se eligió conscientemente `[18, 36]`, o el código es incorrecto si se debería usar `[18, 18]`.

El efecto observable: con `[18, 36]` el sticker se "apoya" en el punto lat/lng (el borde inferior del sticker toca la coordenada), como un globo de chat. Con `[18, 18]` el centro del sticker coincide con el punto. Para un sticker cuadrado sin punta, `[18, 36]` es visualmente extraño: el sticker flota sobre el punto con el borde inferior en la coordenada exacta, lo que geográficamente es menos intuitivo que el centro. En móvil esto puede desplazar visualmente los pines respecto a la ubicación real.

**Fix:** Alinear el valor con la intención declarada. Si la decisión es "bottom-center" (el pie del sticker en la coordenada), el código es correcto pero el PATTERNS.md de referencia estaba incompleto. Si la intención es centrar el sticker sobre la coordenada (más natural para un sticker sin punta), usar:

```ts
iconAnchor: [18, 18], // center-center: el centro del sticker en la lat/lng
popupAnchor: [0, -18], // actualizar popupAnchor consistentemente
```

Aclarar la intención con el equipo de diseño y dejar un comentario que justifique la elección.

### WR-05: E2E — `asAuthenticated` fixture no configura mock de `plant_searches` con `content-range` correcto para `useContextCounts` (4 queries HEAD)

**Archivo:** `e2e/fixtures.ts:183-193` + `e2e/map.spec.ts:24`

**Problema:** La fixture `asAuthenticated` llama `mockPlantHistory()` que mockea `**/rest/v1/plant_searches*` devolviendo `MOCK_HISTORY_ITEMS` para todos los métodos GET. Sin embargo, `useContextCounts` hace 4 queries HEAD (con `head: true`) al mismo endpoint. Playwright intercepta todas con el mismo handler y devuelve `MOCK_HISTORY_ITEMS` (un array) en lugar de una respuesta HEAD vacía con `Content-Range`. El test map.spec.ts resuelve esto correctamente con `page.unroute()` + re-registro del handler antes de cada test.

El problema se da en cualquier otro test futuro que use `asAuthenticated` y espere que `useContextCounts` devuelva counts correctos: la fixture base no distingue GET de HEAD, devuelve body incorrecto para las queries HEAD, y `useContextCounts` puede interpretar `count: null` en todos los buckets. Actualmente los tests de mapa se protegen con `unroute`, pero es una trampa para el siguiente test que no lo haga.

**Fix:** En `mockPlantHistory()` de `fixtures.ts`, añadir distinción por method:

```ts
async function mockPlantHistory(page: Page, items = MOCK_HISTORY_ITEMS) {
  await page.route(
    `${SUPABASE_URL}/rest/v1/plant_searches*`,
    (route) => {
      const method = route.request().method();
      if (method === "DELETE") {
        return route.fulfill({ status: 200, json: [] });
      }
      if (method === "HEAD") {
        // Respuesta para useContextCounts head-only queries
        return route.fulfill({
          status: 200,
          headers: { "content-range": `0-0/${items.length}` },
          body: "",
        });
      }
      return route.fulfill({ status: 200, json: items });
    },
  );
}
```

### IN-01: `trackedOpen` en MapPage no se resetea si el usuario navega fuera y vuelve — `map_opened` no se dispara en visitas posteriores

**Archivo:** `src/pages/MapPage.tsx:45,52-55`

**Problema:** `trackedOpen` es estado local del componente. Cuando el usuario navega a `/mapa` → vuelve → vuelve a `/mapa`, React Strict Mode (dev) o casos con `keep-alive` podrían mantener el componente montado. En la práctica con react-router-dom el componente se desmonta al navegar, así que `trackedOpen` se resetea. Pero el estado es innecesariamente complejo: sería más idiomático y robusto usar un ref para este tipo de "fired-once-per-mount" tracking.

**Fix:**

```tsx
const trackedRef = useRef(false);

useEffect(() => {
  if (isLoading || trackedRef.current) return;
  trackedRef.current = true;
  track("map_opened", { pin_count: plants.length });
}, [isLoading, plants.length]);
```

Eliminar `const [trackedOpen, setTrackedOpen] = useState(false)` y su `setTrackedOpen(true)`.

### IN-02: `use-context-counts.test.ts` — el test de `refetch` asume que las queries mantienen siempre el mismo orden posicional en `Promise.all`

**Archivo:** `src/hooks/use-context-counts.test.ts:39-48`

**Problema:** El mock usa un contador global `queryCounter` y un módulo `% 4` para devolver distintos resultados por posición en `Promise.all`. Este esquema funciona porque `Promise.all` invoca los 4 `supabase.from()` de forma síncrona antes del primer `await`, lo que garantiza el orden. Sin embargo, si en el futuro alguien refactoriza el hook para hacer las queries secuenciales (ej. por rate-limiting), el test seguirá pasando pero el mock devolverá resultados incorrectos silenciosamente. El enfoque es frágil frente a cambios internos del hook.

**Fix (sugerencia menor):** Documentar la asunción en un comentario explícito dentro del test:

```ts
// ASUNCION: Promise.all ejecuta los 4 .from() síncronamente en orden
// (home → wildWith → wildWithout → unclassified). Si el hook cambia a
// queries secuenciales, este mock debe refactorizarse.
```

### IN-03: `splitNameField` en PlantMapSheet no tiene tests unitarios propios

**Archivo:** `src/components/PlantMapSheet.tsx:27-39`

**Problema:** `splitNameField` es una función pure con lógica de parsing (regex con fallback) que se documenta como cobertura de un patrón legacy de datos ("Common (Scientific)"). No está testeada directamente — solo de forma indirecta via el E2E. Según las convenciones del proyecto (`CLAUDE.md`: "Tests para lógica de negocio"), esta función califica como lógica de negocio parseada de datos reales.

**Fix:** Añadir un test unitario al archivo de tests del hook o crear `PlantMapSheet.test.ts`:

```ts
import { describe, it, expect } from "vitest";
// Exportar splitNameField (o testearla via PlantMapSheet props en renderHook)

describe("splitNameField", () => {
  it('parsea "Common (Scientific)" en dos nombres', () => {
    expect(splitNameField("Salvia rosmarinus (Rosmarinus officinalis)")).toEqual({
      commonName: "Salvia rosmarinus",
      scientificName: "Rosmarinus officinalis",
    });
  });
  it("devuelve scientific=null si el formato no coincide", () => {
    expect(splitNameField("Monstera")).toEqual({
      commonName: "Monstera",
      scientificName: null,
    });
  });
  it("maneja paréntesis anidados (nombre científico con var.)", () => {
    expect(splitNameField("Rosa (Rosa canina var. blah)")).toEqual({
      commonName: "Rosa",
      scientificName: "Rosa canina var. blah",
    });
  });
});
```

## Verificado (aspectos correctos que vale la pena registrar)

**Seguridad — sin XSS en PlantMapSheet:** `plant.name`, `plant.imageUrl`, y `plant.createdAt` se renderizan todos via JSX estándar de React (sin `dangerouslySetInnerHTML`). El `build-plant-pin-icon.ts` solo interpola constantes del design system (`hsl(var(--card))`, `hsl(var(--foreground))`) y el emoji estático `🌿` — no hay datos de usuario en el HTML del `divIcon`. Riesgo XSS: nulo.

**Canal de eventos correctamente segmentado:** `App.tsx::PendingClassificationListener` solo escucha `mp:pending-classification-resolved` (que solo dispara `AuthContext` en el flujo anon→auth). El nuevo `mp:plant-context-updated` (que dispara `useClassifyPlant` en clasificación UI) no llega nunca a `PendingClassificationListener`, por lo que no hay navegaciones espurias a `/planta/:id` al clasificar desde `/mis-plantas`.

**Auth race condition fix verificado:** `useWildPlantsWithCoords` llama `setIsLoading(true)` síncronamente en el branch `user !== null` antes del `await` a Supabase (línea 71). Esto cierra la ventana donde `isLoading=false` + `plants=[]` podría causar un redirect prematuro a `/` en `MapPage` durante el intervalo auth-null→auth-loaded.

**`FitBoundsOnMount` usa `useMap()` correctamente:** Implementado como child de `<MapContainer>` usando el hook `useMap()` de react-leaflet (no el patrón `whenCreated` eliminado en v4). El caso borde `pins.length === 0` retorna sin-op. `pins.length === 1` usa `setView` con zoom 14 (D-15). `pins.length > 1` usa `fitBounds` con padding `[40, 40]` (D-14). Landmine #5 correctamente gestionado.

**`100dvh` en MapPage:** La altura del mapa usa `100dvh` (no `100vh`) en ambos lugares donde se declara (loading state y mapa activo, líneas 63 y 80). Landmine #9 resuelto.

**Atribución OSM con `rel="noopener noreferrer"`:** El link de atribución en el `attribution` prop de `TileLayer` incluye correctamente `target="_blank" rel="noopener noreferrer"` (MapPage:94). Licencia ODbL cumplida + protección `window.opener`.

**`BottomTabBar` siempre renderiza (landmine #2):** El componente computa `tabs` vía `useMemo` con `wild_with_coords` del hook, pero no gatilla todo el `<nav>` con un guard de loading — el bar siempre renderiza con al menos "Inicio" y "Mis plantas". Solo la tab "Mapa" está condicionada por `wild_with_coords >= 1`.

**Anónimos correctamente excluidos (D-07):** `useContextCounts` retorna `ZERO` sin tocar Supabase cuando `user === null`. `useWildPlantsWithCoords` retorna `plants: []` sin tocar Supabase. `BottomTabBar` comprueba `user && wild_with_coords >= 1`. Tres capas de protección.

**CSS import order:** `leaflet/dist/leaflet.css` importado ANTES de `./index.css` en `main.tsx` (líneas 4-5), permitiendo que los overrides del proyecto (`.plant-map-pin`, `.leaflet-control-zoom`, etc.) sobrescriban los defaults de Leaflet. Landmine #8 resuelto.

**Leaflet CSS overrides — div icon limpio:** `.plant-map-pin` tiene `background: transparent !important; border: none !important` que elimina el box blanco del default `.leaflet-div-icon`. El `:active` / `:focus-within` `scale(1.1)` tiene su contraparte `@media (prefers-reduced-motion: reduce)` con `transform: none`. Accesibilidad motion correcta.

**E2E cobertura de tile failure (SPEC-AC12):** El test "MapPage survives OSM tile failures" bloquea tiles con `route.fulfill({ status: 503 })` (diferente del abort del happy path) y verifica que el container y los markers siguen visibles + sin toasts. Cubre el comportamiento offline correctamente.
