# Phase 04.1: Mobile Load Time Optimization — Research

**Researched:** 2026-08-12
**Domain:** Frontend performance (mobile-first React SPA + Capacitor WebView + iOS PWA), Supabase Storage image delivery, backfill scripting, in-app perf instrumentation
**Confidence:** HIGH (verified via Supabase docs, code inspection, npm registry, web-vitals docs)

---

## Summary

Phase 04.1 attacks perceived load time in three list screens (`/mis-plantas`, `/regar`, `/mapa`) via **one root fix** (backfill ~124 legacy base64 images to Supabase Storage HTTPS URLs) plus **per-screen local fixes** (`<img loading="lazy" decoding="async" width height>`, tile preconnect, PostHog `perf_screen_loaded` instrumentation).

The dominant weight problem is quantified: 124 rows in `plant_searches.image_url` store data URIs of ~1.5MB each (~186MB of DB payload shipped over the wire when a user opens `/mis-plantas`). Every optimization other than fixing this is a rounding error.

**Critical finding — locked decision D-08 conflicts with plan tier.** Supabase Storage on-the-fly image transformations (`?width=200&quality=70`) are **Pro-plan only** ($25/mo). The Free plan `render/image/` endpoint returns 400/404. The project is on Free (verified: no plan info in docs, no evidence of Pro billing, `.env` unchanged, `plant-images` bucket created with defaults). **See "Critical Blocker" section — the plan MUST choose one of three fallback paths before execution.**

**Primary recommendation:** Fix the DB weight (backfill), then choose fallback strategy for D-08 before touching thumbnails. All other fixes (lazy loading attrs, preconnect, `perf_screen_loaded` event) are green-light and low-risk.

## Critical Blocker: D-08 Assumption vs Supabase Plan Reality

**Verified fact:** `[CITED: https://supabase.com/pricing]` and `[CITED: https://supabase.com/docs/guides/storage/serving/image-transformations]`
> "Image Resizing is currently enabled for Pro Plan and above."

**Verified fact:** `[VERIFIED: supabase/migrations/20260422000000_create_plant_images_bucket.sql]` — the bucket exists but no evidence of Pro upgrade anywhere in repo or planning docs.

**Verified fact:** `[VERIFIED: GitHub issue supabase/cli#3030]` — On plans without transformations enabled, `getPublicUrl(path, { transform: {...} })` returns a URL to `/storage/v1/render/image/public/...` which responds **400/404**.

### What this means concretely

If the project is on Free plan (assumed, since no evidence of Pro):
- Calling `supabase.storage.from('plant-images').getPublicUrl(path, { transform: { width: 200, quality: 70 } })` returns a URL that **404s in production**.
- The user sees broken images or the browser's broken-image icon in `/mis-plantas` and `/regar` cards.
- Backfilled images will be **full-size originals** (2-5 MB each after re-upload — the 124 legacy base64 will be decoded to their real JPEG size). Loading 20 cards means downloading 40-100 MB. **The optimization moves problem from DB payload to CDN payload — it does NOT solve the perf goal.**

### Three fallback paths (Claude's Discretion per DISCUSSION-LOG §Claude's Discretion)

| Path | Cost | Complexity | Time-to-target | Recommendation |
|------|------|------------|----------------|----------------|
| **A. Upgrade to Supabase Pro ($25/mo)** | $25/mo recurring | Trivial (1 click in dashboard) | Same day | ✅ **RECOMMENDED** if project has any revenue/growth intent. Also unlocks Smart CDN, 100GB storage headroom, DB backups, and image transformations exactly as D-08 assumes. CPO context ("shipping v1.1.0 Android beta") suggests product is past hobby stage. |
| **B. Client-side resize before upload + backfill generates thumbs** | $0 recurring | Medium (edit `identify-plant` edge function to upload BOTH `full.jpg` and `thumb.jpg`; backfill script does same for legacy; add `image_thumb_url` column) | +1 plan (~4h) | Viable if Pro upgrade is a hard "no". Requires schema change (`image_thumb_url text`) + edge function edit + more complex backfill. |
| **C. Serve originals with `loading="lazy"` + accept the miss on 200px thumbnail** | $0 | Trivial | Same day | Fastest to ship. Backfilled JPEGs (~200-500KB each after JPEG re-encoding, NOT the 1.5MB base64) + lazy loading may hit TTFC target. **Empirically the largest win here is base64→binary already (~4x smaller after decoding + JPEG re-encoding).** Test after backfill; add thumbnails only if TTFC target is missed. |

**Claude's recommendation for planner:** Ship Path C first, measure, then decide A/B. Rationale:
1. Base64 → binary alone gives ~4x weight reduction (base64 encoding overhead + inline DB payload duplication in queries).
2. `<img loading="lazy">` reduces work to visible viewport only (~3-5 cards initially rendered).
3. If TTFC still misses target post-backfill, upgrade to Pro (Path A) — one dashboard click, no code change needed since D-08 already expects the transform URL pattern.
4. Path B is only justified if CPO refuses Pro upgrade AND Path C fails targets.

**Blocker action required in plan-phase:** Explicit sub-task: "CPO confirms Supabase plan tier. If Free: decide A/B/C. Default = C, upgrade to A if measurement fails."

### Pattern 1: Backfill Script (idempotent one-off)

**What:** Node script (tsx) that pages through `plant_searches` rows with `image_url LIKE 'data:%'`, decodes base64, uploads to `plant-images` bucket, updates the row.

**When to use:** One-time only, run manually by CPO after backup (per D-05).

**Example:**
```typescript
// scripts/backfill-image-urls.ts
// Source: [VERIFIED] mirrors supabase/functions/identify-plant/index.ts lines 381-408
// and Supabase SDK docs [CITED: supabase.com/docs/reference/javascript/storage-from-list]
import "dotenv/config";
import { createClient } from "@supabase/supabase-js";

const SUPABASE_URL = process.env.VITE_SUPABASE_URL!;
const SERVICE_KEY = process.env.SUPABASE_SERVICE_ROLE_KEY!; // NEVER commit; add to .env locally

if (!SUPABASE_URL || !SERVICE_KEY) {
  console.error("Missing env vars. Set VITE_SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY in .env");
  process.exit(1);
}

const supabase = createClient(SUPABASE_URL, SERVICE_KEY, {
  auth: { persistSession: false, autoRefreshToken: false },
});

// ─── BACKUP RUNBOOK (must run BEFORE this script, per D-04) ──────────
// Option A (recommended, uses Supabase CLI):
//   supabase db dump --local=false --data-only --schema=public -f backup-plant_searches-$(date +%Y%m%d).sql
// Option B (SQL Editor in dashboard):
//   Copy the output of:
//   SELECT id, image_url FROM plant_searches WHERE image_url LIKE 'data:%';
//   Save as CSV before running this script.
// Rollback: script does not delete originals. If backfill breaks a row,
// UPDATE plant_searches SET image_url = '<original base64 from backup>' WHERE id = '...';
// ─────────────────────────────────────────────────────────────────────

const BATCH_SIZE = 10;         // 10 uploads in parallel = safe for anon connection pool
const PAGE_SIZE = 50;          // rows fetched per iteration
let processed = 0, skipped = 0, failed = 0;

async function processRow(row: { id: string; user_id: string; image_url: string }) {
  // Idempotency guard (D-04)
  if (!row.image_url.startsWith("data:")) {
    skipped++;
    return;
  }
  const match = row.image_url.match(/^data:([^;]+);base64,(.+)$/);
  if (!match) {
    console.error(`[${row.id}] malformed data URI — skipping`);
    failed++;
    return;
  }
  const [, mediaType, base64Data] = match;
  const ext = mediaType === "image/png" ? "png" : "jpg"; // simplified — real code inspects mediaType

  // Decode base64 to Uint8Array (mirror of edge function pattern)
  const binaryStr = Buffer.from(base64Data, "base64");
  const bytes = new Uint8Array(binaryStr);

  // Upload with the same {user_id}/{ts}-{rand}.jpg pattern as identify-plant/index.ts:383
  const fileName = `${row.user_id}/${Date.now()}-backfill-${Math.random().toString(36).slice(2, 8)}.${ext}`;
  const { error: uploadErr } = await supabase.storage
    .from("plant-images")
    .upload(fileName, bytes, {
      contentType: mediaType,
      cacheControl: "31536000",
      upsert: false,
    });
  if (uploadErr) {
    console.error(`[${row.id}] upload failed:`, uploadErr.message);
    failed++;
    return;
  }
  const { data: urlData } = supabase.storage.from("plant-images").getPublicUrl(fileName);

  // UPDATE row — only after successful upload (leaves original data: URI in place if UPDATE fails)
  const { error: updateErr } = await supabase
    .from("plant_searches")
    .update({ image_url: urlData.publicUrl })
    .eq("id", row.id);
  if (updateErr) {
    console.error(`[${row.id}] update failed:`, updateErr.message);
    failed++;
    return;
  }
  processed++;
  if (processed % 10 === 0) console.log(`  … ${processed} processed`);
}

async function main() {
  console.log("=== Backfill: base64 → Storage HTTPS ===");
  console.log("BACKUP first (see comment block). Ctrl-C now if you haven't.");
  await new Promise((r) => setTimeout(r, 5000));

  let offset = 0;
  while (true) {
    const { data: rows, error } = await supabase
      .from("plant_searches")
      .select("id, user_id, image_url")
      .like("image_url", "data:%")
      .range(offset, offset + PAGE_SIZE - 1);

    if (error) {
      console.error("Fetch failed:", error);
      process.exit(1);
    }
    if (!rows || rows.length === 0) break;

    console.log(`\n--- Page ${Math.floor(offset / PAGE_SIZE) + 1}: ${rows.length} rows ---`);

    // Process in batches of BATCH_SIZE for parallelism
    for (let i = 0; i < rows.length; i += BATCH_SIZE) {
      const batch = rows.slice(i, i + BATCH_SIZE);
      await Promise.all(batch.map(processRow));
    }

    offset += PAGE_SIZE;
  }

  console.log(`\n=== Done: ${processed} migrated · ${skipped} already-HTTPS · ${failed} failed ===`);
  if (failed > 0) {
    console.log("Re-run to retry failed rows (script is idempotent).");
    process.exit(1);
  }
}

main().catch((e) => {
  console.error("Fatal:", e);
  process.exit(1);
});
```

  }

### Pattern 2: TTFC measurement with Performance API

**What:** Measure the time from the browser starting navigation to the first render that shows real content (not spinner). Fire PostHog event.

**When to use:** In each of the 3 pages, exactly once per mount, only when `isLoading === false` and content is present.

**Example:**
```typescript
// src/hooks/use-perf-screen-loaded.ts
// Source: [CITED: MDN Performance API — performance.now()]
// https://developer.mozilla.org/en-US/docs/Web/API/Performance/now
import { useEffect, useRef } from "react";
import { track } from "@/lib/track";

/**
 * Fires PostHog event `perf_screen_loaded` exactly once per mount, on the
 * first render where isLoading=false and content is present.
 *
 * Measures TTFC as (time of first content render) - (navigationStart).
 * Uses performance.now() which is monotonic and independent of clock drift.
 * The number is the time from when the browser started processing the
 * navigation to this route until React committed a paint with real content.
 *
 * For SPA route changes, `navigation.startTime` remains the initial page
 * load. For soft navigations this is still a useful proxy — it captures
 * the total user-perceived load time (bundle parse + hydrate + query).
 *
 * NOTE: The event fires from useEffect, which runs AFTER the browser
 * paints. So the number is a slight over-estimate of true first-paint
 * time. This is acceptable — over-estimates are conservative, and we
 * want to include any post-mount data readiness lag.
 */
export function usePerfScreenLoaded(
  screen: "mis-plantas" | "regar" | "mapa",
  isReady: boolean,
  extraProps: Record<string, unknown>,
): void {
  const fired = useRef(false);
  useEffect(() => {
    if (!isReady || fired.current) return;
    fired.current = true;
    // performance.now() is time since navigation started (monotonic ms with sub-ms precision).
    const ttfc_ms = Math.round(performance.now());
    track("perf_screen_loaded", {
      screen,
      ttfc_ms,
      ...extraProps, // e.g. { plants_count: plants.length }
    });
  }, [isReady, screen, extraProps]);
}
```

**Usage in `/regar`:**
```typescript

```

**Usage in `/mis-plantas`:**
```typescript

```

**Usage in `/mapa`:**

### Pattern 3: Thumbnail URL helper (D-08 strategy encapsulated)

**What:** Centralize the D-08 transformation logic in ONE file. If we later switch strategy (A/B/C), only this file changes.

**Example:**
```typescript
// src/lib/thumbnail-url.ts
// Source: [CITED: Supabase Storage image transformations docs]
// https://supabase.com/docs/guides/storage/serving/image-transformations
//
// D-08: Return a 200px-wide thumbnail URL for a Supabase Storage HTTPS URL.
// Pass-through for legacy (data:), non-Supabase, or already-transformed URLs.
//
// ⚠️ Depends on Supabase Pro plan. On Free plan the render/image/ endpoint
// returns 400/404. See RESEARCH.md § Critical Blocker.
export function thumbnailUrl(url: string, width = 200, quality = 70): string {
  if (!url) return url;
  if (url.startsWith("data:")) return url; // legacy — pass through
  // Rewrite /storage/v1/object/public/... → /storage/v1/render/image/public/...?width=…
  const objectPath = "/storage/v1/object/public/";
  const renderPath = "/storage/v1/render/image/public/";
  if (!url.includes(objectPath)) return url; // not a Supabase Storage URL
  const rendered = url.replace(objectPath, renderPath);
  const sep = rendered.includes("?") ? "&" : "?";
  return `${rendered}${sep}width=${width}&quality=${quality}`;
}
```

/>

### Anti-Patterns to Avoid

- **useLayoutEffect for the perf event.** `[CITED: react.dev/reference/react/useLayoutEffect]` "blocks the browser from painting until your code runs". This actively worsens TTFC. Use `useEffect`.
- **Setting `image_url = NULL` after successful upload.** Breaks history if the storage upload succeeds but the UPDATE fails mid-transaction. The script must ONLY set the new URL after upload is confirmed.
- **Running backfill in a Postgres migration (D-05 forbids it).** Migration runs on every deploy — a fresh Vercel deploy would either fail (idempotency) or waste compute. Keep as separate one-off script.
- **Adding a `CHECK image_url LIKE 'https://%'` constraint before backfill completes.** Would fail with the 124 legacy rows still base64. Only add after `SELECT COUNT(*) FROM plant_searches WHERE image_url LIKE 'data:%' = 0`. Even then — defer to a later phase; not in scope here per Deferred Ideas.
- **Migrating hooks to React Query without mounting QueryClientProvider.** Currently NO `QueryClientProvider` exists in the app (`[VERIFIED: grep -rn QueryClient src/App.tsx src/main.tsx` returned nothing). Adding React Query requires provider setup + refactoring 3+ hooks + updating tests. Out of scope for perf phase.
- **Hardcoding `width={80}` in the img element without `height={80}`.** Prevents CLS reservation — `[CITED: web.dev CLS best practices]` — both attributes are required.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Base64 decoding in Node | Custom base64 parser | `Buffer.from(str, "base64")` (Node built-in) | Streaming-safe, faster than atob for large payloads |

## Common Pitfalls

### Pitfall 1: Assuming Free-tier features work on Pro-only endpoints
**What goes wrong:** `getPublicUrl(path, { transform: {...} })` returns a URL. On Free plan, that URL 404s.
**Why it happens:** SDK is silent — it constructs the URL client-side without checking plan capability. `[CITED: GitHub issue supabase/cli#3030]`
**How to avoid:** Before running the plan, CPO confirms Supabase plan. If Free, choose fallback A/B/C.
**Warning signs:** Broken image icons in cards after backfill; PostHog `perf_screen_loaded` shows LOWER `ttfc_ms` (browser gives up on failed images fast) but `<img onerror>` fires; users report "las fotos han desaparecido".

### Pitfall 2: Backfill script eats memory on large base64 rows
**What goes wrong:** A 1.5MB base64 string ≈ 1.1MB Buffer. Loading 50 rows in a page = ~55MB in RAM. Fine on a laptop; nothing on a serverless function would run this anyway.
**Why it happens:** SELECT `*` returns the full data URI in memory.
**How to avoid:** SELECT only needed columns (`id`, `user_id`, `image_url`). Process rows in batches of 10 concurrently (not 50). Free the buffer after upload (JS GC will handle it as long as you don't hoard references).
**Warning signs:** Node process OOM at ~1.5GB RAM (default heap). If seen, drop BATCH_SIZE or run node with `--max-old-space-size=4096`.

### Pitfall 3: `<img>` without explicit dimensions causes CLS during lazy-load
**What goes wrong:** Browser doesn't know image size until it downloads. Layout shifts when image arrives. Cumulative Layout Shift score climbs.
**Why it happens:** `loading="lazy"` triggers download on viewport approach; layout was computed pre-load with 0×0 image.
**How to avoid:** Always set `width` and `height` (or `aspect-ratio` CSS) whenever lazy-loading. `[CITED: web.dev CLS 2026 guide]`
**Warning signs:** Scroll janks; card sizes jump as user scrolls; Chrome DevTools Performance panel shows layout shifts.

### Pitfall 4: `perf_screen_loaded` fires before actual content is on screen
**What goes wrong:** `useEffect` runs after commit but before browser paints images. Event reports ttfc_ms that doesn't include image download time.
**Why it happens:** React's paint model — commit happens, then browser paints on next frame.
**How to avoid:** Fire the event when data (`plants.length > 0`) is ready. Include `plants_count: 0` case explicitly if empty state is valid. Recognize the event measures "content-shell readiness" not "images fully loaded" — that's OK, D-10's TTFC target is about text/card structure appearing, not image bytes on wire.
**Warning signs:** Numbers seem too low (<200ms) — likely event fires before images load. If wanting image-inclusive metric, listen to `<img onload>` on the first card. **Recommended: keep the simple pattern; TTFC of "text/card shell" is what D-10 is really targeting.**

### Pitfall 5: Preconnect to wrong number of subdomains
**What goes wrong:** Adding 10+ preconnects wastes browser resources. Adding only 1 misses Leaflet's `{a,b,c}.tile` load balancing.
**Why it happens:** `[CITED: web.dev preconnect guide]` recommends limit of 4-6 preconnects total.
**How to avoid:** Preconnect exactly the 3 subdomains Leaflet uses (a/b/c.tile.openstreetmap.org). Confirm `crossorigin` attribute since tiles are cross-origin.
**Warning signs:** Lighthouse reports "preconnect to unused origin" — remove the extras.

### Pitfall 6: React Query added to codebase but no provider mounted
**What goes wrong:** `useQuery` call throws "No QueryClient set" at runtime.
**Why it happens:** `@tanstack/react-query` is in `package.json` but nothing calls it (verified by grep).
**How to avoid:** **Do NOT migrate hooks to React Query in this phase.** Provider setup is 30min; migrating 3 hooks with existing event-driven refetch logic (see `useHomePlants` `mp:plant-watered` listener) is a full refactor. Save for a dedicated "state management cleanup" phase.
**Warning signs:** Runtime error in dev after migration; tests fail because they don't wrap in QueryClientProvider.

### Pitfall 7: Backfill runs against wrong DB (dev vs prod)
**What goes wrong:** Script authored against `.env` may target the dev project. Running against prod requires prod credentials.
**Why it happens:** `.env` typically holds dev keys. Prod keys must be set explicitly.
**How to avoid:** Log the Supabase URL at script start. Require typed confirmation ("yes migrate PROD") before proceeding. CPO reviews the URL before typing yes.
**Warning signs:** Script reports "0 rows to migrate" when 124 were expected — wrong project. Or the reverse — migrated dev-only test rows.

### React Query — evaluation and recommendation

**Current state (verified by grep):**
- `@tanstack/react-query` 5.83.0 in `package.json`

**What React Query would give us:**
- Cache between navigations (user goes Home → Regar → Home → Regar → no second fetch)
- Automatic background refetch on window focus (mobile useful for returning to app)
- Deduplication of concurrent queries
- Standard loading/error/data pattern

- Update existing event listeners: `mp:plant-watered`, `mp:plant-context-updated`, etc. from manual `refetch()` to `queryClient.invalidateQueries(['home-plants'])` — this is subtle, easy to break reactivity
- Update all 3 hook test files (verified they exist: `use-home-plants.test.ts` etc.) — significant test refactor since tests currently mock `supabase.from()` calls
- Update WildPlant mounted-ref pattern that guards against race conditions from WebKit auth bootstrap (see `use-home-plants.ts:78-82`) — React Query handles this natively but the migration needs care

**Recommendation: DEFER to a follow-up phase.**

Rationale:
1. Perf gain is real but marginal for <200 rows (cache miss = one fast query anyway).
2. Migration risk: existing event-driven reactivity (which is not idiomatic React Query) is load-bearing for the calendar (`mp:plant-watered` → optimistic UI in `PlantWateringCard.tsx:143`).
3. Scope creep: this phase is about *perceived* load time (paint speed, image weight). React Query helps navigation-cache, not cold-load.
4. `@tanstack/react-query` should not be removed from `package.json` — leave it installed for future use.

If the planner has 4+ hours of budget above and beyond the perf work, migrate ONE hook (`usePlantHistory` — highest-value cache since it's the largest list) as a proof-of-concept and defer the rest. Do NOT touch `useHomePlants` (calendar reactivity is critical UX).
