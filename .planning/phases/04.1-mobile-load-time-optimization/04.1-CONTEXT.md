# Phase 04.1: Mobile Load Time Optimization - Context

**Gathered:** 2026-08-12
**Status:** Ready for planning

<domain>
## Phase Boundary

Reducir el tiempo percibido de carga de las 3 pantallas de listado en mobile: `/mis-plantas` (historial), `/regar` (calendario) y `/mapa` (descubrimientos wild). Fix raíz del peso de imágenes legacy + fixes locales por pantalla. Alcance fijo: solo estas 3 rutas. Nuevas capacidades (búsqueda, filtros, virtualization como feature) → otras fases.

</domain>

<decisions>
## Implementation Decisions

### Alcance y estrategia de release
- **D-01:** Las 3 pantallas se optimizan juntas y se shipean en UN solo release final (no por pantalla individual). El PR de merge a `main` cierra la sub-fase completa.
- **D-02:** Orden de trabajo interno: (a) backfill fotos legacy → primero, es fix raíz común, (b) cambios frontend por pantalla → en paralelo tras (a), (c) instrumentación + verificación conjunta → último. Sin releases intermedios.

### Root fix vs parche
- **D-03:** Se ataca la raíz. Script de backfill migra las ~124 filas legacy con `image_url LIKE 'data:%'` a URLs HTTPS en Supabase Storage (bucket `plant-images` ya existe desde Phase 1 Plan 01-03). Fin de la deuda técnica, no un parche.
- **D-04:** El script es idempotente (skip rows que ya son HTTPS) para poder ser corrido de nuevo si algo falla a mitad. Backup completo de `plant_searches` ANTES de ejecutar.
- **D-05:** El script se ejecuta MANUALMENTE por la CPO (no en migración SQL automática) — es one-off, no debe correr por deploy.

### Loading state
- **D-06:** Se MANTIENE el spinner Leaf animado centrado que ya existe en `/mis-plantas` y `/regar`. No se implementan skeleton screens. Diferido a phase futura si tras medir vemos que la percepción sigue siendo lenta.
- **D-07:** `/mapa` no gana loading state visual (los tiles de OpenStreetMap ya dan feedback progresivo por sí solos).

### Thumbnails e imágenes
- **D-08:** Se usa la **transformación on-the-fly de Supabase Storage** (`?width=200&quality=70` sobre la URL) para las cards de las 3 pantallas. La foto original se sigue usando en `/planta/:id` (detalle). Cero cambio en el esquema DB, cero cambio en el path de upload nuevo.
- **D-09:** Todos los `<img>` de las 3 pantallas llevan `loading="lazy"`, `decoding="async"` y `width`/`height` explícitos (evita layout shift, mejora CLS).

### Umbrales de éxito (objetivos concretos)
- **D-10:** Un fix se considera exitoso si cumple TODOS los siguientes en un iPhone real de la CPO, en condiciones 4G (network throttled en DevTools o test real):
  - `/mis-plantas`: Time-to-First-Content (primera card visible) < **1.5s** p50 con 20 plantas
  - `/regar`: Time-to-First-Content < **1.5s** p50 con 5-10 plantas casa
  - `/mapa`: Pins render < **2s** p50 tras cargar la ruta
  - Scroll a 60fps en las 3 pantallas con lista de 50+ items (aplicable a `/mis-plantas` y `/regar`)
- **D-11:** Los números se ajustan durante execute si en la primera medición reveal-baseline resultan irrealistas. La CPO acepta márgenes ±25% si el fix es notablemente mejor que el estado actual.

### Instrumentación (measurement)
- **D-12:** Nuevo evento PostHog `perf_screen_loaded` con props `{screen: 'mis-plantas' | 'regar' | 'mapa', ttfc_ms: number, plants_count: number, app_version, app_platform}`. Disparado al primer render con contenido real. Sirve para verificar en usuarios reales que el fix funciona post-deploy.
- **D-13:** El evento se dispara TANTO en iOS PWA como en Android Capacitor. `app_version` + `app_platform` ya son super-properties tras sub-fase 03.2 → se agregan solos.

### Claude's Discretion
- Paginación de queries: solo si en discovery aparecen usuarios con >100 fotos. Con volumen típico esperado (<50) no compensa la complejidad.
- Virtualization (react-window, tanstack-virtual): defer. Solo si scroll 60fps NO se cumple con las mejoras de imagen. La CPO no pide virtualization como feature.
- Cache de queries: usar los patrones existentes de React Query (ya en el stack); no montar cache adicional.
- Backup del `plant_searches` antes del backfill: se puede hacer con `pg_dump` desde el dashboard de Supabase o `supabase db dump`. Documentar el comando exacto en el script.
- Rollback plan del backfill: como es idempotente y no borra el data original hasta confirmar, se puede parar a mitad sin riesgo. Documentado en el script.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`src/pages/History.tsx`** (`/mis-plantas`): renderiza `<img src={item.imageUrl}>` sin lazy, sin dimensiones. Cambio directo con `loading="lazy"` + `width`/`height`.
- **`src/components/PlantWateringCard.tsx`** (usado en `/regar`): mismo patrón.
- **`src/pages/MapPage.tsx`** (`/mapa`): imágenes NO se muestran en el listado — solo pins. El coste viene de leaflet + tiles OSM. Fix distinto: probablemente `<link rel="preconnect" href="tile.openstreetmap.org">` + medir si esa es la causa real.
- **`browser-image-compression`** (ya instalado desde Phase 4) — no aplica aquí (es para subida, no download), pero confirma que la app puede procesar imágenes off-thread.
- **`useHomePlants`, `usePlantHistory`, `useWildPlantsWithCoords`**: ya existen. Verificar en el planner si tienen problemas de re-fetch innecesario o queries que traen columnas no usadas.
- **`.planning/phases/03.1-plant-map-v0/`**: patrones de mock e2e con leaflet reutilizables para la verificación.

### Established Patterns
- **React Query** ya en el stack (`@tanstack/react-query 5.83.0`) pero NO se usa en los hooks de las 3 páginas — usan `useState` + `useEffect` + `supabase.from(...)` directo. El planner debe evaluar si migrar a React Query da beneficios (cache entre navegaciones) sin ser scope creep.
- **Super-properties PostHog** (`app_version`, `app_platform`) agregadas automáticamente desde sub-fase 03.2 — solo llamar `track()` normal.
- **Idempotencia en migraciones**: convención del proyecto (todas las SQL migrations son `IF NOT EXISTS`). El script one-off de backfill debe seguirlo (skip rows ya HTTPS).

### Integration Points
- **Supabase Storage bucket `plant-images`** ya existe (Phase 1 Plan 01-03). Reutilizable directamente.
- **Edge function `upload-plant-image`** (Phase 1 Plan 01-03): sirve de referencia para el path/naming convention, pero el script backfill llamará al SDK directamente (no via edge function — no es user-facing).
- **RLS `plant_searches`**: `auth.uid() = user_id` para SELECT/UPDATE. El script backfill se ejecuta con `service_role_key` desde local — bypasea RLS legítimamente para la migración one-off.

</code_context>

<specifics>
## Specific Ideas

- La CPO reportó el problema el **2026-08-12** con lenguaje coloquial: "tarda mucho en cargar" en las 3 pantallas. No hay una métrica reportada por ella — de ahí los umbrales objetivos en D-10 para poder cerrar la phase sin ambigüedad.
- **Estilo de trabajo autónomo:** la CPO explicitó "no me molestes ni preguntes nada que no sea estrictamente necesario". El planner y executor deben tomar decisiones técnicas por sí solos siguiendo las convenciones del proyecto, y solo interrumpir para decisiones de PRODUCTO (ej. copy, comportamiento visible al usuario).
- Preferencia clara por **fix raíz sobre parche** (D-03) — consistente con el estilo previo (Phase 3 UI fixes atacaron causas, no síntomas).

</specifics>

<deferred>
## Deferred Ideas

- **Skeleton screens** — si tras esta phase la percepción sigue lenta pese a las métricas cumplidas, considerar phase separada de "perceived performance / skeleton UI".
- **Virtualization de listas** (react-window / tanstack-virtual) — solo si 60fps no se cumple con las mejoras de imagen. Ni se toca en esta phase.
- **React Query migration en los hooks de listado** — si el planner considera que da beneficios sin coste, puede incluirlo como parte de esta phase; si es refactor grande, defer.
- **Búsqueda y filtros server-side en `/mis-plantas`** (hoy son client-side sobre lista completa) — mejora de perf a gran escala, pero es NUEVA capability. Belongs to su propia phase.
- **Preload/preconnect a Supabase + PostHog** en el `<head>` — mejora TTFB. Considerar como optimización menor en el plan.
- **Skeleton para `/mapa` mientras carga tiles OSM** — evaluar si el tiempo sin feedback es problema real; por ahora se mantiene sin loading state.

</deferred>
