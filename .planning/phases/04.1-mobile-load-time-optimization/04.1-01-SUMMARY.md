## Prerequisite unblock — bucket creation

The bucket `plant-images` did not exist in production, even though migration `20260422000000_create_plant_images_bucket.sql` was checked into `supabase/migrations/`. The migration had never been pushed via `supabase db push`.

Applied the following SQL manually in Supabase Dashboard SQL Editor (idempotent version of the original migration):

```sql
insert into storage.buckets (id, name, public)
values ('plant-images', 'plant-images', true)
on conflict (id) do nothing;

drop policy if exists "Users can upload own images" on storage.objects;
create policy "Users can upload own images"
  on storage.objects for insert
  with check (bucket_id = 'plant-images' and auth.uid()::text = (storage.foldername(name))[1]);

drop policy if exists "Service role can upload anonymous images" on storage.objects;
create policy "Service role can upload anonymous images"
  on storage.objects for insert
  with check (bucket_id = 'plant-images' and (storage.foldername(name))[1] = 'anonymous');

drop policy if exists "Public read access for plant images" on storage.objects;
create policy "Public read access for plant images"
  on storage.objects for select
  using (bucket_id = 'plant-images');
```

**Discovered issue for follow-up (not blocking this phase):** since the bucket never existed in production, ALL identifications since Phase 1 have been storing images as base64 fallback silently. Every new identification going forward will use the bucket correctly. To confirm, check that `identify-plant` edge function upload path succeeds in the next few days.

## Architectural shape

- **One-off Node/tsx script** — `scripts/backfill-image-urls.ts`. Run manually by CPO via `npm run backfill:images` with `SUPABASE_SERVICE_ROLE_KEY` set locally. Never runs automatically.
- **Idempotent** — filters rows by `image_url LIKE 'data:%'` at each run; skips rows already migrated.
- **Non-destructive** — never NULLs `image_url` until Storage upload confirmed 200 OK; the UPDATE happens only after upload success.
- **Batched** — fetches 50 rows per iteration, uploads 10 concurrently. For ~98 rows this meant 2 runs of ~15 seconds each.
- **Security** — `SUPABASE_SERVICE_ROLE_KEY` used to bypass RLS legitimately (one-off migration script, no user-facing runtime). Key removed from `.env` after execution.
