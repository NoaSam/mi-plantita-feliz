<objective>
Migrar las ~124 filas legacy de `plant_searches.image_url` que están como `data:image/jpeg;base64,...` a URLs HTTPS del bucket `plant-images` de Supabase Storage. Cero cambio en el path de upload nuevo. Script one-off ejecutado manualmente por la CPO (D-05) tras backup DB (D-04).

Purpose: Fix raíz del peso de imágenes en las 3 pantallas (`/mis-plantas`, `/regar`, `/mapa`). Cada base64 pesa ~1.5MB × 124 filas = ~186MB de payload DB que hoy se descarga en las queries de listado. Migrar a HTTPS reduce el payload a ~100 bytes (URL) × 124 + delegar los blobs al CDN de Storage. Esto es el prerequisito bloqueante para que los fixes frontend (Plan 02) tengan impacto medible.

Output:
- `scripts/backfill-image-urls.ts` (~120 líneas, idempotente, batched, safe rollback)
- `scripts/backfill-image-urls.test.ts` (tests unitarios de helpers puros)
- `package.json` — nueva entry `"backfill:images": "tsx scripts/backfill-image-urls.ts"`
- Al final del plan: la CPO ejecuta manualmente `npm run backfill:images` (checkpoint) tras backup DB
- Estado esperado post-run: `SELECT COUNT(*) FROM plant_searches WHERE image_url LIKE 'data:%'` devuelve 0
</objective>

         console.log("=== Backfill: base64 → Storage HTTPS ===");
         console.log("Target: " + SUPABASE_URL);
         console.log("BACKUP first (see comment block). Ctrl-C now if you haven't.");

             .from("plant_searches")
             .select("id, user_id, image_url")
             .like("image_url", "data:%")
             .range(offset, offset + PAGE_SIZE - 1);

           if (error) {
             console.error("Fetch failed:", error);
             process.exit(1);

           if (!rows || rows.length === 0) break;

             await Promise.all(batch.map(processRow));
