# Phase 02.1: Code Review Report

**Reviewed:** 2026-05-13
**Depth:** quick (pattern-matching + targeted reads on data-integrity paths)
**Files Reviewed:** 23
**Status:** issues_found

## Summary

Quick scan found **one show-stopper**: the new `context` column has no RLS UPDATE policy on `plant_searches`, so every classify / revert call from the authenticated client will be silently denied by Postgres. Combined with a stuck UI state when revert fails, the core classification feature is non-functional end-to-end. Three more BLOCKERs cover navigation guard bypass, stale-state-after-prop-change in `PlantResultView`, and unvalidated cross-account writes via the pending-classification flow. Standard hygiene issues (debug `console.log` in production path, unused cancellation flag, stale closure on `id`) are listed as WARNINGs.

## Critical Issues

### CR-01: Missing RLS UPDATE policy on `plant_searches` — `context` writes are silently rejected [BLOCKER]

**Files:**
- `supabase/migrations/20260506000000_add_context_to_plant_searches.sql` (whole file)
- `supabase/migrations/20260404000000_create_plant_searches.sql:17-29`
- `src/hooks/use-classify-plant.ts:18-21`, `30-34`
- `src/lib/pending-classification.ts:71-74`

**Issue:** RLS is enabled on `plant_searches` and only three policies exist: SELECT, INSERT, DELETE. There is **no UPDATE policy**. Postgres RLS denies any operation that lacks a matching policy, so every `supabase.from("plant_searches").update({ context: ... })` from the client will fail with an RLS violation. That means:

1. `useClassifyPlant.classify()` → always returns `{ ok: false }` → user always sees toast "No se pudo guardar. Reintenta." → the morph/banner state machine in `PlantResultView` never advances past `cards`.
2. `useClassifyPlant.revert()` → undo button is broken.
3. `processPendingClassification()` after sign-up — the anon→auth wall flow — silently fails to write the intent and just navigates the user to the plant detail with `context = 'unclassified'`.

End result: the entire phase 02.1 feature (the classification state machine, the wall flow, and the auto-settle after signup) does not work in production. Local dev with service role may mask this.

**Fix:** Add an UPDATE policy in the same migration (or a new follow-up migration before merge):
```sql
create policy "Users can update own searches"
  on plant_searches for update
  using (auth.uid() = user_id)
  with check (auth.uid() = user_id);
```
Both `using` and `with check` are required so the row must belong to the caller both before and after the update (prevents reassigning `user_id`). Add an integration test that calls `classify()` against a real Supabase instance with anon JWT and asserts the row was updated.

### CR-02: `PlantResultView` state is initialized lazily from props — stale UI when `plant` prop changes [BLOCKER]

**File:** `src/components/PlantResultView.tsx:46-50`

**Issue:** `phase`, `pendingAction`, and `committedContext` are seeded from `plant.context` only on the very first render via lazy `useState` initializers. If the same component instance receives a *different* `plant` prop later (which happens whenever the user navigates between two `/planta/:id` routes without unmount, because React Router reuses the component for parameterized routes), the state from the previous plant leaks into the new render:

- Plant A is `home` → `committedContext = "home"`, `phase = "banner"`.
- User clicks a thumbnail in the `UnclassifiedSection`, navigating to plant B (context `unclassified`).
- `PlantResultView` re-renders with `plant.context = "unclassified"`, but `phase` is still `"banner"` from plant A → banner displays with plant B's id and plant A's committed context. Tapping "Cambiar" sets phase to `"cards"` and now writes against plant B's id — outwardly correct, but the user briefly sees the wrong status, and on first paint the banner copy is wrong for the data.

**Fix:** Resync derived state when `plant.id` changes. Either:
```tsx
useEffect(() => {
  setPhase(derivePhase(plant.context));
  setPendingAction(null);
  setCommittedContext(
    plant.context === "home" || plant.context === "wild" ? plant.context : null,
  );
}, [plant.id, plant.context]);
```
or use the route param as the React `key` on the parent (`<PlantResultView key={plant.id} plant={plant} />` in `PlantDetail.tsx:32`) so the component remounts per plant.

### CR-03: `handleUndo` strands the UI in `morph` phase on revert failure [BLOCKER]

**File:** `src/components/PlantResultView.tsx:84-93`

**Issue:** Flow when revert fails:
1. User taps "Deshacer". `ClassificationMorph.handleUndo` clears the 5-second commit timer and calls `onUndo()` (`PlantResultView.handleUndo`).
2. `revert(plant.id)` returns `{ ok: false }`. Code toasts and `return`s **without** restoring state — `phase` stays `"morph"`, `pendingAction` stays set.
3. The morph component is still mounted, but its commit timer was cleared in step 1 and `useEffect`'s `arm()` only runs on mount, so `onCommit` will never fire.

UI is stuck on the green "Añadida a tu jardín" pill with no way to recover. Meanwhile, the database row is still `context = action` (because the original `classify` UPDATE succeeded). The user has a wrong-or-correct DB state with a frozen UI either way.

**Fix:** Treat revert-failure as "DB still committed" and let the timer-driven `onCommit` path settle:
```tsx
const handleUndo = async () => {
  if (!pendingAction) return;
  const { ok } = await revert(plant.id);
  if (!ok) {
    toast.error("No se pudo deshacer. La planta sigue en tu jardín.");
    // DB state is still classified — promote to committed banner.
    setCommittedContext(pendingAction);
    setPendingAction(null);
    setPhase("banner");
    return;
  }
  setPendingAction(null);
  setPhase("cards");
};
```
Pair with CR-01 — without the UPDATE policy, *every* revert hits this dead path.

### CR-04: `processPendingClassification` writes `context` without verifying ownership of `plant_search_id` [BLOCKER — security]

**File:** `src/lib/pending-classification.ts:67-92`

**Issue:** The function reads `plant_search_id` and `action` from sessionStorage, then runs `UPDATE plant_searches SET context = action WHERE id = plant_search_id`. The only safeguard is RLS at the database layer.

Current RLS state (see CR-01): no UPDATE policy → all writes denied (which is why this isn't an active exploit *today*, but only because the whole feature is broken).

When CR-01 is fixed by adding `using (auth.uid() = user_id)`, this code path becomes safe **only if the row's `user_id` was already set to `auth.uid()` by `claimAnonymousSearches()` immediately before**. The ordering in `AuthContext.tsx:52-53` is correct (claim → process), but:
- If `claimAnonymousSearches()` partially fails (e.g., the row's `anonymous_id` does not match the sessionStorage one, because the user signed in to a different account than the one that originally identified the plant), the row is never claimed. Then `processPendingClassification` will still try the UPDATE, RLS will deny it, the warning will be logged, and the `mp:pending-classification-resolved` event will *not* fire — so the listener in `App.tsx:30-43` never navigates the user to the plant. The user lands on `/mis-plantas` with no feedback that their intent was lost.
- Worse: there is no validation that the `anonymous_id` stored in sessionStorage matches `getAnonymousId()` at processing time. A malicious page could write any `plant_search_id` to `mp_pending_classification` before the user signs in. Once RLS-by-user_id is in place that limits the attack to rows owned by the signing-in user, but it still lets a script-attacker mutate the `context` of an arbitrary plant of the just-signed-in user.

**Fix:**
1. Before calling `claim_anonymous_searches`, verify the sessionStorage `anonymous_id` equals `getAnonymousId()`; if not, clear and bail out.
2. Make `processPendingClassification` gate the UPDATE with `.eq("user_id", session.user.id)` so it cannot mutate a row that wasn't owned by this user.
3. If the UPDATE affects 0 rows (RLS denial or wrong owner), emit a recoverable toast and skip the navigation event.

```ts
const { data, error } = await supabase
  .from("plant_searches")
  .update({ context: pending.action })
  .eq("id", pending.plant_search_id)
  .eq("user_id", session.user.id)   // belt + RLS suspenders
  .select("id")
  .maybeSingle();

if (error || !data) {
  clearPendingClassification();
  return null;
}
```

### WR-02: `useUnclassifiedCount` declares a cancellation flag it never reads from inside async work

**File:** `src/hooks/use-unclassified-count.ts:61-68`

**Issue:** The `cancelled` flag is set in the useEffect cleanup but only checked **after** `await load()` resolves, while `load()` itself (lines 25-59) freely calls `setCount`, `setRecent`, and `setIsLoading` regardless of whether the component is still mounted. If the user navigates away during the fetch, React will warn about "state update on an unmounted component" and any in-flight setters race with the next mount's state.

**Fix:** Either pass the flag into `load` and guard every setState, or use an `AbortController` against the supabase client request, or simply move the `await load()` into a fire-and-forget call and let `load` swallow late updates via a ref-tracked mounted boolean.

### WR-03: `usePlantById` types `id` as `string` but the caller passes `string | undefined`

**Files:** `src/hooks/use-plant-by-id.ts:16`, `src/pages/PlantDetail.tsx:9-11`

**Issue:** `useParams<{ id: string }>()` returns `id: string | undefined` regardless of the generic — react-router-dom v6's types intentionally widen route params. The hook signature `usePlantById(id: string)` is therefore lying, and the `if (!id)` defensive check inside the hook is the only thing keeping it from a runtime `supabase.from(...).eq("id", undefined)` query (which Postgres would interpret as `id = NULL` and the maybeSingle() would silently return null — that path already lands on `notFound`, but it adds an unnecessary round-trip).

**Fix:** Type the parameter honestly and short-circuit in the caller:
```ts
export function usePlantById(id: string | undefined): UsePlantByIdReturn { ... }
```
or in PlantDetail: `if (!id) { navigate("/", { replace: true }); return null; }` before mounting the hook.
