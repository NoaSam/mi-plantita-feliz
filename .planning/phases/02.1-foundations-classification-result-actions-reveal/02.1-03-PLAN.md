    The new implementation:
    1. Counts rows owned by the anonymous_id BEFORE the RPC (the RPC itself returns void per existing types).
    2. Calls the RPC.
    3. On success, fires `anon_searches_claimed` with `{ count }` only if count > 0 (avoid noise events).
    4. Returns `{ count }` so callers can know how many rows were claimed.

    Per D-15, the count is queried before the RPC because the RPC doesn't return count. Per the ASYNC nature of `count: 'exact'` in PostgREST, this is a single small query against the `anonymous_id` index — fast.

    Replacement code (lines 24-35 of `src/services/auth.service.ts`):
    ```typescript
    /**
     * Transfers anonymous plant_searches rows to the newly authenticated user.
     * Fires `anon_searches_claimed` PostHog event with row count (D-15, SPEC-10).
     * Returns the count of rows that were claimed (0 if no anonymous_id or RPC failed).
     */
    export async function claimAnonymousSearches(): Promise<{ count: number }> {
      if (!hasAnonymousId()) return { count: 0 };
      const anonymousId = getAnonymousId();

      // Count BEFORE the RPC — RPC doesn't return count, and after RPC the rows are
      // owned by user_id so a count by anonymous_id would return 0.
      const { count, error: countError } = await supabase
        .from("plant_searches")
        .select("*", { count: "exact", head: true })
        .eq("anonymous_id", anonymousId);

      if (countError) {
        console.warn("count anonymous searches failed:", countError.message);
      }

      const { error } = await supabase.rpc("claim_anonymous_searches", {
        p_anonymous_id: anonymousId,
      });
      if (error) {
        console.warn("claim_anonymous_searches failed:", error.message);
        return { count: 0 };
      }

      clearAnonymousId();

      const claimedCount = count ?? 0;
      if (claimedCount > 0) {
        track("anon_searches_claimed", { count: claimedCount });
      }
      return { count: claimedCount };
    }
    ```

<threat_model>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Supabase Auth → AuthContext | `onAuthStateChange` receives the new session; client trusts Supabase's signature on the JWT. |
| AuthContext → CustomEvent dispatch | Custom DOM event crosses module boundary to the App layer (Plan 07 listener). |
| RPC `claim_anonymous_searches` → DB | RPC runs with the authenticated user's RLS context; performs the user_id transfer. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02.1-12 | Spoofing | Custom DOM event `mp:pending-classification-resolved` could be dispatched by any script on the page | accept | Same-origin browser script execution can already do anything the user can do. The event's `detail.plant_search_id` is then used in `navigate(...)`; if a spoofed event triggers navigation to a row the user can't see, RLS denies it and `usePlantById` (Plan 02) returns `notFound`, which surfaces a toast. No data leak, no privilege escalation. |
| T-02.1-13 | Information disclosure | `anon_searches_claimed` event count could leak to PostHog | accept | Count is non-PII (just an integer). PostHog ingest is via the existing wrapper with consent gating; the event respects consent like all others. |
| T-02.1-14 | Race condition | `processPendingClassification` runs UPDATE concurrently with `usePlantHistory` initial fetch — fetch may see pre-UPDATE state | mitigate | The dispatched event lets Plan 07 navigate AFTER the UPDATE resolves. The destination route mounts `PlantResultView` via `usePlantById` (a fresh fetch), which returns the post-UPDATE row. Stale history list is acceptable for the brief window before navigation completes; History is not the post-auth landing page. |
| T-02.1-15 | Repudiation | A different user logs in than the one whose intent was stored (CONTEXT.md security_threat_model_requirement) | mitigate | After `claimAnonymousSearches`, the row's `user_id` is set to whatever user just authenticated (not necessarily the original intent's owner). The UPDATE then runs under that user's RLS context. If user A creates the intent but user B logs in and inherits the anonymous_id (impossible without sharing localStorage), B will own the classification — which is correct because B has the device's anonymous rows. Cross-user theft requires localStorage access that already implies device compromise. |
| T-02.1-16 | Tampering | RPC failure leaves anonymous_id unconsumed but the wall sessionStorage was cleared | accept | Per D-13 the wall closes itself when the user picks signup/login. If the RPC fails, the user can re-tap a card after retry; the anonymous_id is preserved (clearAnonymousId only runs on RPC success). The pending classification key was already cleared by `processPendingClassification` regardless of RPC outcome — this is a small UX degradation (must re-tap), not a security issue. |
