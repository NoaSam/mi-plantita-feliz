## 2. Diseño propuesto: columna `context` en `plant_searches`

### Por qué columna y no tabla nueva

Para v0 (foundations + calendar v0 + map v0) **no hace falta** una tabla separada `user_plants`. La razón:
- "Solo identificar" → la fila ya se crea (auto-save existente). Solo necesitamos marcarla para que NO aparezca en superficies extras.
- "Añadir a mis plantas" → necesita que la fila aparezca en la lista de calendario.
- "Guardar descubrimiento" → necesita que la fila aparezca en el mapa.

Una sola columna en `plant_searches` cubre los 3 casos sin nueva tabla. Si v1+ requiere apodos/edición/historial de riegos, **entonces** se introduce `user_plants` con FK a `plant_searches`.

### Propuesta de columna

```sql
alter table plant_searches
  add column context text not null default 'unclassified'
    check (context in ('home', 'wild', 'unsaved', 'unclassified'));
```

**Valores:**
| Valor | Significado | Acción del usuario | Visible en |
|---|---|---|---|
| `home` | Planta del usuario, va al calendario | "Añadir a mis plantas" | Home (Mis plantas), historial |
| `wild` | Descubrimiento exterior, va al mapa | "Guardar descubrimiento" | Mapa, historial |
| `unsaved` | Identificación puntual, no se quiere guardar | "Solo identificar" | Solo historial general |
| `unclassified` | Sin clasificar (default) | — (rows existentes pre-migración o sin acción aún) | Historial general; reveal banner invita a clasificar |

**Nombre `context`** elegido sobre alternativas (`usage_mode`, `kind`, `surface`) por brevedad y alineamiento con el lenguaje del re-encuadre dual-mode.

### Índice nuevo (para queries de superficies)

```sql
create index plant_searches_user_context_date
  on plant_searches (user_id, context, created_at desc)
  where user_id is not null;
```

Cubre las queries:
- Calendario v0: `where user_id = ? and context = 'home' order by created_at desc`
- Mapa v0: `where user_id = ? and context = 'wild' and lat is not null order by created_at desc`

### Plan de backfill

Triple safe:

1. **Esquema:** `default 'unclassified'` aplicado por la migración a TODAS las filas existentes en una sola operación.
2. **Sin downtime:** `ALTER TABLE ADD COLUMN` con `DEFAULT` es fast-path en Postgres ≥11 (no reescribe filas para columnas nullable con default constante; aquí no es nullable, pero el default constante también es fast-path desde 11). Riesgo de bloqueo: despreciable para tamaños actuales.
3. **Adopción gradual:** los usuarios re-clasifican manualmente desde el detalle de cada planta vieja, motivados por el banner de reveal en Phase 02.1.

**Estimación:** las filas existentes son del orden de docenas a cientos (proyecto reciente, beta). El cambio se aplica en milisegundos.

### Migración propuesta (esqueleto)

```sql
-- supabase/migrations/2026MMDD000000_add_context_to_plant_searches.sql

alter table plant_searches
  add column context text not null default 'unclassified'
    check (context in ('home', 'wild', 'unsaved', 'unclassified'));

create index plant_searches_user_context_date
  on plant_searches (user_id, context, created_at desc)
  where user_id is not null;

-- No hay UPDATE explícito: el default 'unclassified' se aplica a todas las filas existentes
-- en la operación de ALTER TABLE.
```

### Impacto en RLS

**Ninguno**. Las policies actuales filtran por `user_id = auth.uid()`. La nueva columna no afecta authorization. Cada usuario sigue viendo solo sus filas, y el contexto es un atributo más a leer/escribir dentro de ese alcance.

### Impacto en el edge function `identify-plant`

El edge function inserta hoy en `plant_searches` SIN el campo `context`. Después de la migración, el INSERT tendrá `default 'unclassified'` aplicado automáticamente. El usuario clasifica desde el cliente (PATCH/UPDATE) cuando elige una de las 3 acciones en el result screen. **No hace falta cambiar el edge function en esta migración** — el cambio es separable y atómico.

### Impacto en flujo de anónimos

El `claim_anonymous_searches(p_anonymous_id text)` no toca `context`, por lo que las filas migradas conservan su valor (`unclassified` por default, o lo que el usuario haya clasificado pre-login). **Comportamiento correcto sin cambios adicionales**.

### Impacto en TypeScript types

`src/integrations/supabase/types.ts` necesita regenerarse tras la migración (`supabase gen types`). Esto añade `context: string` a `Row`/`Insert`/`Update` de `plant_searches`. Tarea trivial dentro del plan de Phase 02.1.

## 3. Coordinación con Phase 2 (Prompt Optimization)

Phase 2 (Prompt Optimization) debe entregar `watering_interval_days` como campo numérico estructurado dentro de la respuesta de la IA. Hoy ese dato no se persiste en ninguna columna de `plant_searches`.

**Opciones:**
- **A) Phase 2 añade la columna `watering_interval_days`** (numeric). Phase 02.1 hereda eso.
- **B) Phase 02.1 añade `watering_interval_days` junto con `context`** en una sola migración.

Recomendación: **A**, porque conceptualmente Phase 2 es la dueña del dato (es quien lo produce). Phase 02.1 lo consume sin tener que añadirlo. Esto se decide formalmente al planificar Phase 2.

## 4. Riesgos y mitigaciones

| Riesgo | Probabilidad | Mitigación |
|---|---|---|
| Filas existentes quedan en `unclassified` y el calendario/mapa parecen vacíos | Alta | Banner de reveal en Phase 02.1 invita a clasificar; clasificación retroactiva accesible desde detalle |
| Usuario clasifica como `home` y luego cambia de opinión | Alta | Permitir cambiar contexto desde detalle (UPDATE simple, RLS lo cubre) |
| Anónimo clasifica, hace login, sus filas migran pero el contexto se "olvida" | Bajo (RPC actual NO toca context) | RPC ya hace solo `set user_id`; verificar que sigue así tras la migración |
| Los valores del check fail (typo en cliente) | Bajo | TypeScript types regenerados + el cliente usa enum/constants, no strings literales |
| Una migración futura añade un valor nuevo y rompe el CHECK | Medio | Documentar el set de valores permitidos en un solo lugar (`src/lib/plant-context.ts` por ejemplo) y actualizar CHECK + types juntos |

## 5. Decisiones que aún quedan abiertas (para discutir al planificar Phase 02.1)

1. **¿"Solo identificar" persiste la fila o no?**
   - Opción A: persistir con `context='unsaved'` (mantiene flujo actual de auto-save, solo cambia visibilidad).
   - Opción B: NO insertar en `plant_searches` cuando el usuario elige "Solo identificar" (cambia el flujo del edge function — el insert se delega al cliente tras la elección).
   - Recomendación: **A** para v0. Mantiene compatibilidad con `model_evaluations` (que necesita la FK a `plant_searches.id`) y simplifica el edge function. La fila vive como "trazabilidad" pero no aparece en surfaces.

2. **¿"Añadir a mis plantas" requiere también un nickname desde el principio?**
   - v0: NO. Se usa `name` (nombre común generado por la IA). El nickname se difiere a v1+.

3. **¿La acción de clasificación se aplica también a identificaciones del historial pre-existente?**
   - Sí. La pantalla de detalle de cualquier identificación (incluso vieja) muestra las 3 acciones cuando `context = 'unclassified'`.

4. **¿Cuál es el comportamiento del banner de reveal post-update para usuarios autenticados que no tienen ninguna identificación clasificada?**
   - Dos sub-casos:
     - Usuario con historial → banner explica las novedades, link a "ver mi historial y clasificar".
     - Usuario sin historial → banner se omite (no hay nada que clasificar todavía).

## 6. Resumen ejecutivo (para verificación rápida)

- Tabla afectada: **solo `plant_searches`** (añadir 1 columna + 1 índice).
- Migración: **una sola**, en `supabase/migrations/`, sin downtime.
- Backfill: **automático** vía DEFAULT `'unclassified'`. Cero riesgo a usuarios actuales.
- RLS: **sin cambios**. Las policies existentes cubren el caso.
- Edge function: **sin cambios** en esta migración. La clasificación es operación del cliente.
- TypeScript types: **regenerar** tras la migración (1 comando).
- Phase 2 dependency: **`watering_interval_days`** debe llegar antes que Phase 02.1, pero es separable de esta migración.

**Phase 02.1 puede planificarse con esta información.** No hay bloqueantes externos.
