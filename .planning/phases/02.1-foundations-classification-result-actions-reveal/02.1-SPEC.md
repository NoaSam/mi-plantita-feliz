# Phase 02.1: Foundations: Classification + Result Actions + Reveal — Specification

**Created:** 2026-05-05
**Ambiguity score:** 0.18 (gate: ≤ 0.20)
**Requirements:** 10 locked

## Goal

Las identificaciones de plantas se pueden etiquetar como **`home`** (para el calendario v0) o **`wild`** (para el mapa v0) desde el resultado, el detalle accedido vía historial y desde la sección "Sin clasificar" en home; los usuarios anónimos ven la opción pero la acción está protegida por un wall de login que preserva su intención y la ejecuta automáticamente tras el alta.

## Background

**Estado actual del esquema** (verificado en `02.1-SCHEMA-AUDIT.md`):
- `plant_searches` no tiene columna de contexto. Las identificaciones se guardan sin atributo de "casa vs silvestre".
- `lat` y `lng` ya existen (preparado para mapa).
- `claim_anonymous_searches(text)` RPC ya existe — transfiere filas anónimas al usuario auth tras login.

**Estado actual de la UI**:
- `src/components/PlantResultView.tsx` renderiza la pantalla de resultado: hero photo + nombre + accordion (Qué es / Cómo cuidarla / Qué le pasa).
- `src/pages/Index.tsx` (home) es minimalista: hero `<Leaf>` + saludo + subtítulo + `<PhotoCapture>`. Sin sección de historial ni nada relacionado con clasificación.
- `src/pages/History.tsx` lista identificaciones sin indicadores de estado.
- `src/lib/track.ts` provee `track(event, props)` que solo dispara cuando hay consentimiento de analytics.

**Trigger** del trabajo: el re-encuadre dual-mode del producto (`.planning/notes/re-encuadre-dual-mode-decision.md`) introduce dos modos de uso (casa / explorar) que necesitan un mecanismo de clasificación por planta. Sin esta fase, las features posteriores (Calendar v0 — Phase 3, Plant Map v0 — Phase 03.1) no tienen datos que mostrar.

**Diseño visual** (locked en sketches 001/002/003):
- Sketch 001 winner A: 2 cards apiladas pedagógicas con icono + título + descripción de la consecuencia.
- Sketch 002 winner C: tras tap, la card pulsada se transforma en sitio (verde primary + ✓ + Deshacer); a los 5s colapsa a un banner persistente "Está en tu jardín/mapa · Cambiar".
- Sketch 003 winner D: sección home condicional (logged-in + count > 0), historial con chips, wall de login para anónimos solo desde el resultado de su identificación recién hecha.

## Requirements

1. **Schema migration**: Añadir columna `context` a `plant_searches` con CHECK constraint + índice compuesto.
   - Current: `plant_searches` no tiene columna `context`.
   - Target: Columna `context text not null default 'unclassified' check (context in ('home','wild','unclassified'))` + índice `plant_searches_user_context_date (user_id, context, created_at desc) where user_id is not null`.
   - Acceptance: La migración aplica en staging sin errores. Las filas existentes quedan con `context = 'unclassified'`. Un INSERT sin especificar `context` succeed con default. Un INSERT con `context = 'foo'` falla por CHECK. El índice aparece en `pg_indexes`.

2. **ClassificationCards en result screen para plantas sin clasificar**: La pantalla de resultado renderiza 2 cards de acción encima del accordion existente cuando `context = 'unclassified'`.
   - Current: `PlantResultView.tsx` renderiza solo el accordion.
   - Target: Cuando la planta tiene `context = 'unclassified'`, se renderiza `ClassificationCards` (sketch 001 winner A) entre el nombre de la planta y el accordion. El accordion **permanece** intacto debajo.
   - Acceptance: Component test verifica que las cards renderizan para `context = 'unclassified'` y NO renderizan para `'home'` o `'wild'`. El accordion renderiza siempre.

3. **ClassificationMorph al tocar una card**: Tap en una card transforma esa card en sitio (sketch 002C) y permite deshacer durante 5 segundos.
   - Current: No existe UI de clasificación.
   - Target: Tap en una card → llama `update plant_searches set context = X where id = Y`; la card pulsada se reemplaza por `ClassificationMorph` (fondo primary green + ✓ + título "Añadida a tu jardín/mapa" + botón "Deshacer"); la otra card se atenúa (`opacity: 0.35; pointer-events: none`). A los 5000 ms sin tap en Deshacer, ambas cards se reemplazan por `PersistentClassificationBanner`.
   - Acceptance: E2E test toca una card, confirma que `ClassificationMorph` aparece y que `Deshacer` revierte el contexto a `'unclassified'` y muestra las 2 cards otra vez. Otro test toca una card, espera 6 s, y confirma que aparece el banner persistente.

4. **PersistentClassificationBanner para plantas ya clasificadas**: Cuando `context` es `'home'` o `'wild'`, la pantalla de resultado renderiza un banner "Está en tu jardín/mapa · Cambiar" en lugar de las 2 cards.
   - Current: No existe el banner.
   - Target: `PersistentClassificationBanner` renderiza un banner cream con borde sticker, icono apropiado (🪴 para home, 📍 para wild), texto "Está en tu jardín" / "Está en tu mapa", y botón "Cambiar" que revierte el render a las 2 cards (no cambia el `context` hasta el siguiente tap).
   - Acceptance: Component test renderiza el banner para ambos contexts con copy correcto. Clic en "Cambiar" muestra las 2 cards. Clic en una card actualiza `context` y vuelve al morph→banner flow.

5. **UnclassifiedSection condicional en home**: La home renderiza una sección "Sin clasificar (N)" SOLO cuando el usuario está logueado Y tiene ≥1 fila con `context = 'unclassified'`.
   - Current: `Index.tsx` no tiene sección post-CTA.
   - Target: Después del botón de cámara, condicional: si `auth.user && unclassified_count > 0`, se renderiza `UnclassifiedSection` con header "Sin clasificar (N)" + grid de hasta 4 thumbnails + link "Ver todas" + hint copy. Si `unclassified_count === 0` o el usuario es anónimo, la sección no se renderiza (no empty state).
   - Acceptance: Con usuario logueado y 23 filas unclassified, sección renderiza con count "(23)". Con usuario logueado y 0 filas unclassified, la sección NO renderiza. Con usuario anónimo y cualquier conteo, la sección NO renderiza.

6. **HistorySummary y ContextChip en History page**: Cada entrada del historial tiene un `ContextChip` indicando su `context`, y el header de la página muestra un resumen agregado.
   - Current: `History.tsx` lista las identificaciones sin chip ni resumen.
   - Target: Cada item tiene un chip a la derecha del nombre+fecha con 3 variantes visuales: `chip-unclassified` ("Sin clasificar"), `chip-home` ("🪴 Jardín"), `chip-wild` ("📍 Descubrimiento"). Encima de la lista, `HistorySummary` muestra "De N plantas: X jardín · Y descubrimientos · Z sin clasificar".
   - Acceptance: Visual snapshot test confirma que cada fila renderiza el chip correcto según `context`. El sumario agrega correctamente los conteos. **No** se renderiza ningún filtro UI (solo chips visuales).

7. **AnonClassificationWall al tocar una card siendo anónimo**: Cuando un usuario anónimo toca una card en el resultado de su identificación, se abre un bottom sheet pidiendo registro/login.
   - Current: La pantalla de resultado se muestra igual a anónimos y logueados; no existe el wall.
   - Target: Cuando `auth.user === null`, tap en una `ClassificationCard` no actualiza `context` — en su lugar abre `AnonClassificationWall` (bottom sheet con icono 🔒, copy "Necesitas una cuenta", botones "Crear cuenta" / "Iniciar sesión" / "Volver sin guardar"). La intención de clasificación (`'home'` o `'wild'`) se guarda en estado del cliente (sessionStorage o react state) hasta resolverse el flujo de auth.
   - Acceptance: E2E como anónimo, tap en card "Mis plantas" abre el wall. La fila en `plant_searches` NO cambia su `context` en este punto. La intención `'home'` queda guardada en el cliente.

8. **Auto-clasificación tras login/signup desde el wall**: Al completar registro o login desde el wall, la clasificación pendiente se ejecuta automáticamente.
   - Current: `claim_anonymous_searches(anonymous_id)` existe pero no hay flujo encadenado con clasificación.
   - Target: Tras signup o login exitoso desde el wall, en este orden: (a) se ejecuta `claim_anonymous_searches(anonymous_id)` (transfiere user_id), (b) se ejecuta `update plant_searches set context = <intención guardada> where id = <plant_search_id>`, (c) se navega de vuelta a la pantalla de resultado, (d) la pantalla muestra el `PersistentClassificationBanner` (no morph — ya no hay ventana de undo).
   - Acceptance: E2E: anónimo identifica, toca card "Mis plantas", completa signup, vuelve al resultado. Verificar en DB: `user_id = new_user.id`, `anonymous_id = NULL`, `context = 'home'`. UI muestra banner "Está en tu jardín · Cambiar".

9. **PlantResultView es la pantalla canónica para resultado y detalle**: Tanto la pantalla post-identificación como la accedida desde el historial o `UnclassifiedSection` renderizan a través del mismo componente `PlantResultView`.
   - Current: `PlantResultView` solo se invoca desde `Index.tsx` con el resultado en memoria.
   - Target: `UnclassifiedSection` thumbnails, link "Ver todas", e items del historial navegan a una ruta que carga la fila por `id` y renderiza el mismo `PlantResultView`. La info original (Qué es / Cómo cuidarla / Qué le pasa) se preserva siempre. Las cards o el banner aparecen condicionalmente según `context`.
   - Acceptance: Navigation test confirma que el mismo componente renderiza para ambos flujos. El accordion siempre presente. La sección de clasificación (cards o banner) aparece en el lugar correcto según `context`.

10. **PostHog events fire según contrato**: Los 10 eventos documentados en `docs/posthog-events.md` § Phase 02.1 emiten en los puntos correctos con sus propiedades.
    - Current: Ninguno de los 10 eventos está cableado.
    - Target: Los 10 eventos (`classification_action_clicked`, `classification_undo_clicked`, `classification_completed`, `classification_change_clicked`, `unclassified_section_shown`, `unclassified_section_clicked`, `history_item_clicked`, `anon_classification_wall_shown`, `anon_classification_wall_action`, `anon_searches_claimed`) emiten via `track()` con las propiedades especificadas. `unclassified_section_shown` se deduplica una vez por sesión.
    - Acceptance: Manual QA con PostHog Live Events visualiza cada evento durante el flujo de prueba. Las propiedades coinciden con el contrato. `unclassified_section_shown` aparece una sola vez aunque la home se monte varias veces en la sesión.

## Boundaries

**In scope:**
- Migración SQL: añadir columna `context` + índice compuesto `(user_id, context, created_at desc)`
- Regenerar `src/integrations/supabase/types.ts` tras migración
- 7 componentes nuevos: `ClassificationCards`, `ClassificationMorph`, `PersistentClassificationBanner`, `UnclassifiedSection`, `HistorySummary`, `ContextChip`, `AnonClassificationWall`
- Modificar `PlantResultView.tsx` para integrar la sección de clasificación condicionalmente (encima del accordion existente)
- Modificar `Index.tsx` (home) para renderizar `UnclassifiedSection` condicionalmente (solo logged-in + count > 0)
- Modificar `History.tsx` para añadir `HistorySummary` (header) y `ContextChip` (por item)
- Crear ruta para "abrir planta desde historial/sección" que monte `PlantResultView` por id
- Wire del flujo anon: estado para guardar intención, integración con flujo de auth, ejecución encadenada de `claim_anonymous_searches` + UPDATE de `context` post-auth
- Wire de los 10 eventos PostHog según contrato en `docs/posthog-events.md`
- Texto UI en español

**Out of scope:**
- **Calendar v0 UI** — entrega de Phase 3 (esta fase solo prepara los datos)
- **Plant Map v0 UI** — entrega de Phase 03.1 (esta fase solo prepara los datos)

- **Bulk multi-select en historial** — defer v1+, sketch 003 variante B explícitamente descartada
- **Filtros/sort UI en History page** — confirmado en SPEC interview round 1; solo chips visuales en v0
- **Settings opcional para ocultar UnclassifiedSection** — defer v1+
- **Sketch 004 (re-classify desde detalle)** — confirmado redundante; la pantalla 3 del sketch 003D ya cubre el patrón
- **Drag/swipe gestures para clasificar** — defer v1+, no es lenguaje establecido del producto
- **Notificaciones push de "X plantas sin clasificar"** — fuera de alcance, no hay notifications stack en el proyecto
- **Cambios en RLS de `plant_searches`** — las policies existentes ya cubren la nueva columna
- **Cambios en `claim_anonymous_searches` RPC** — el RPC se mantiene; el UPDATE de `context` es un paso adicional del cliente, no del RPC
- **Cambios en `model_evaluations`** — analytics no se rompe; el FK sigue apuntando a `plant_searches.id`
- **Onboarding screens / tutorial** — explícitamente disuelto del roadmap (Phase 4 eliminada)
- **Reveal banner / modal sobre lanzamiento** — sketch 003 variantes B y C descartadas a favor de la sección sticky condicional
- **Editar `watering_interval_days`** — entrega de Phase 2 (Prompt Optimization), no de esta
- **Apodos para plantas** — defer a Calendar v1+

## Constraints

- **Design system existente** (locked): Fraunces (display) + Outfit (body), 18 px base, line-height 1.6. Paleta cream + verde oliva profundo + coral. `--radius: 1rem`, `--shadow-press: 4px 4px 0px 0px hsl(100 70% 10%)`. NO se introducen nuevos tokens visuales; los componentes nuevos consumen los que ya existen en `tailwind.config.ts` + `src/index.css`.
- **Tracking** vía `src/lib/track.ts` exclusivamente. PostHog ya inicializa solo con consent; nuevo código NO inicializa nada por su cuenta.
- **Migración Postgres** debe ser fast-path: `ALTER TABLE ADD COLUMN ... NOT NULL DEFAULT 'unclassified'` aprovecha el optimizer de Postgres ≥11 para no reescribir filas. Cero downtime esperado.
- **RLS** de `plant_searches` no se modifica. Las policies actuales filtran por `user_id = auth.uid()` y la columna nueva entra automáticamente bajo ese alcance.
- **`claim_anonymous_searches` RPC** no se modifica.
- **Idioma de la UI** en español. Variables, componentes y commits en inglés (per CLAUDE.md).
- **Mobile-first**. Diseño objetivo a 414 px de ancho. Desktop secundario.
- **Vertical slice release**: la migración + componentes + eventos se publican como UN solo release. No hay release intermedio donde "se clasifica pero no aparece nada".
