```typescript
const FALLBACK_NAME        = "Planta no identificada";
const FALLBACK_DESCRIPTION = "No se pudo identificar la planta. Intenta con otra foto más clara.";
const FALLBACK_CARE        = "Asegúrate de que la foto muestre bien la planta.";
const FALLBACK_DIAGNOSIS   = "No hay suficiente información para un diagnóstico.";

function isFallbackResult(info: PlantInfo): boolean {
  return (
    info.name        === FALLBACK_NAME &&
    info.description === FALLBACK_DESCRIPTION &&
    info.care        === FALLBACK_CARE &&
    info.diagnosis   === FALLBACK_DIAGNOSIS
  );
}

function parseAIResponse(text: string): PlantInfo | null {
  let parsed: Record<string, unknown> | null = null;

  try {
    parsed = JSON.parse(text);
  } catch {
    const jsonMatch = text.match(/\{[\s\S]*\}/);
    if (jsonMatch) {
      try { parsed = JSON.parse(jsonMatch[0]); } catch { /* invalid JSON */ }
    }
  }

  if (!parsed) return null;

  const toStr = (v: unknown, fb: string) =>
    typeof v === "string" && v.trim() ? v : fb;

  return {
    name: toStr(parsed.name, FALLBACK_NAME),
    description: toStr(parsed.description, FALLBACK_DESCRIPTION),
    care: toStr(parsed.care, FALLBACK_CARE),
    diagnosis: toStr(parsed.diagnosis, FALLBACK_DIAGNOSIS),
  };
}
```

**Extend `parseAIResponse` with a `toIntOrNull` helper** following the same shape as `toStr`. Pattern to add inside the function (per `<code_context>` Reusable Assets + `<specifics>` 1-60 days range):

```typescript
const toIntOrNull = (v: unknown): number | null => {
  const n = typeof v === "number" ? v : typeof v === "string" ? Number(v) : NaN;
  if (!Number.isFinite(n)) return null;
  const int = Math.round(n);
  if (int < 1 || int > 60) return null;  // out-of-range → likely hallucination
  return int;
};

return {
  name: toStr(parsed.name, FALLBACK_NAME),
  description: toStr(parsed.description, FALLBACK_DESCRIPTION),
  care: toStr(parsed.care, FALLBACK_CARE),
  diagnosis: toStr(parsed.diagnosis, FALLBACK_DIAGNOSIS),
  watering_interval_days: toIntOrNull(parsed.watering_interval_days),
};
```

### `supabase/migrations/2026MMDD000000_add_watering_interval_days_to_plant_searches.sql` (CREATE)

**Analog:** `supabase/migrations/20260506000000_add_context_to_plant_searches.sql` (most recent and only other `ALTER plant_searches` with a default + check).

**Full analog file:**

```sql
-- Add context to plant_searches to support dual-mode classification.
-- Values: 'home' (Mis plantas / calendar) | 'wild' (Descubrimiento / map) | 'unclassified' (default)
-- See: .planning/phases/02.1-foundations-classification-result-actions-reveal/02.1-SCHEMA-AUDIT.md
alter table plant_searches
  add column if not exists context text not null default 'unclassified'
    check (context in ('home', 'wild', 'unclassified'));

-- Composite partial index for surface queries (calendar, map, home unclassified count).
-- WHERE user_id is not null skips anonymous rows that don't surface in user UIs.
create index if not exists plant_searches_user_context_date
  on plant_searches (user_id, context, created_at desc)
  where user_id is not null;
```

**Pattern to follow for new migration:**

```sql
-- Add watering_interval_days to plant_searches: structured frequency used by Calendar v0 (Phase 3).
-- Nullable: model returns null when it can't determine the value with confidence (D-02).
-- Range 1-60 days enforced at the edge function via toIntOrNull; check constraint is belt-and-suspenders.
-- Historical rows stay NULL; backfill deferred (see CONTEXT.md § Claude's Discretion).
-- See: .planning/phases/02-prompt-optimization/02-CONTEXT.md
alter table plant_searches
  add column if not exists watering_interval_days integer
    check (watering_interval_days is null or (watering_interval_days >= 1 and watering_interval_days <= 60));
```

**Critical convention** (per `supabase/MIGRATION_CONVENTIONS.md` lines 53-55):

> "**For migrations that do NOT create tables (alter, indexes, data)** — Sin cambios. El nuevo default solo afecta a `CREATE TABLE`."

This means: **NO `GRANT` block is needed** for this migration because it's an `ALTER TABLE`, not `CREATE TABLE`. `plant_searches` is a pre-October-2026 table and inherits its existing grants. Do NOT add a `GRANT` block — would be a no-op at best, misleading at worst.

**Pitfalls:**
- File name format: `YYYYMMDDHHMMSS_*.sql` with the timestamp at the start. The convention across the 9 existing migrations is `YYYYMMDD000000_descriptive_name.sql` (zero-padded HHMMSS). Use today's date.
- Use `add column if not exists` (idempotent — matches the convention from the `context` migration line 5 and `consensus_match_level` migration line 4).
- DO NOT add an index for `watering_interval_days` unless there's a query that filters/sorts by it. Calendar v0 will likely filter by `user_id + context='home'` and consume `watering_interval_days` as a payload field, not a filter key.
- After this migration runs, regenerate `src/integrations/supabase/types.ts` via `supabase gen types typescript --linked > src/integrations/supabase/types.ts`. Do NOT hand-edit the generated file.

**Pitfalls:**
- Dot-prefix the filename (`.benchmark-golden-set.json`) to match the project's convention for "tool-local committed state" files (`.error-baseline.json` is the precedent). NOT in `.gitignore`; it IS committed.
- 20-25 items per `<specifics>` "Tamaño del golden set". Larger sets blow up benchmark runtime (each item = 3 model calls; at ~3-5s per call that's 3-7 min for 20 items).
- `scientificName` in the ground truth uses the same normalization the consensus uses: lowercased, no parens, no cultivar quotes. This way comparing against `extractScientificName(model.name)` is a direct string-eq (or via `normalizeScientificName` for tier 2).
- Hand-labeling is owner work (per `<decisions>` D-12: "~1-2h de la dueña del producto"). The executor delivers the script + empty/seed JSON skeleton, NOT the labels.
